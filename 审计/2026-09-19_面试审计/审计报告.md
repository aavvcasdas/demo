### 2.2 实际主链与“只是文档承诺”的部分

```text
用户题目 / 账号定位
   ↓
story 路由 → story-short-write
   ↓
style-resolution + 人生副本实录 + 通用骨架
   ↓
benchmark-recall → 拆文报告/节点/手法/原文/meta
   ↓
事实来源 / 设定 / 状态台账 / 场面表 / 大纲批准
   ↓

   ↓
fuben_run.py 的 8 个确定性步骤：
  design → facts → setting_years → hype
  → draft → review → lint → AI-patterns
   ↓
fuben-review：人工/模型语义审查、并排读、首屏、听感
   ↓
TTS / 剪辑 / 逐镜 QA / 人工发布批准
   ↓
真实发布回执 → 同窗口数据快照 → 分析 → 有证据再调整规则
```

**只有其中的校验段已经是可直接执行的程序链。**`fuben_loop.py` 的 `design/draft/review` 是检查命令，并不自行生成正文、规划工具调用、返修再试或发布。名字里有 loop，不等于已经有 Agent 运行循环。

当前 `AGENTS.md:3,38–41` 明确支持 generic/solo：没有宿主 hooks/custom agents 也能由当前 Agent 读取文件执行。根目录 `.claude/.codex/.opencode/.agents/.story-deployed` 未发现，**不是部署失败的证明**；正确表述是“当前为文件式执行，未证明运行时硬拦截和独立多 agent 已生效”。

专项 skill 并非完全不可达：专项引用和 `fuben_run.py:46` 会提示调用它。但 `AGENTS.md:9–23` 的入口表漏列它，泛化“审查”容易进入另一份契约。建议显式路由：**副本稿→fuben-review；其他小说→story-review；需要时再追加通用审查，而不是互相替代。**

## 三、值得保留的七项优势

1. **不是只会拼 prompt。**已有拆文资产、设定、台账、原文、审核与发布材料，能把创作经验落到可复查文件。
2. **从“人物遭遇”转向“触发—动作—状态变化”。**对沉沦、习惯、系统规则题，这比强行设置反派和反杀更适合《人生副本》。最新 78 的第一次 AI 成功、后来依赖、最后只取回三行控制权，就是较好的落地。
3. **有事实锁与数字守恒意识。**彩票玩法、票数、年月、金额之类可以确定判断的错误，用程序先过滤非常值得做。已有 T1/T2/T4/T5 红绿样本并非摆设，本次真实运行通过。
4. **知道回看原文，而不只记“爆款公式”。**拆文目录的原文、节点和手法分离，对标视图与原库分离，有利于保持来源和创作项目边界。
5. **开始用语料反向检查规则。**44 篇单篇原文中，字数带违例 11、行数带违例 8、环境/身体词窗口违例 11，促成部分规则降级。这比为了让规则永远正确而责怪所有稿件成熟。
6. **存在诚实边界的好规范。**自检要标注、证据不足用 PROVISIONAL、审查与修改分离、成片必须人看、数据先核口径、原稿保留，方向正确；78 v2 报告也明确承认“自检、待 HR 复核”。
7. **作品已有具体可感的场面，不是纯参数合成。**76 的虾落盘、鼾声突然停下；77 从冠军笑容到外界判词反噬；78 的说明书、合租水电与回车键，均有叙事功能。

要保留的是这些能力，而不是每一次修稿后新加的永久阈值。

## 四、优先处理的工程与流程问题

**以下 P0/P1/P2 是本报告的工作优先级，不与仓库文学审核的 S1/S2 混用。**P0=下次依赖自动验收/数据归因前；P1=下一批交付前；P2=扩量前。

### E01 · P0 · review 把 False 打成 OK

- **位置**：`scripts/fuben_loop.py:328–361`。
- `show(label, value, ok)` 的若干调用，把布尔判断放进 `value`，把非空解释字符串放进 `ok`。Python 将字符串判为真。
- **独立复现**：临时五行正文、没有因果触发和结尾状态动作，删除呼应表后，单独的 review 返回 0：

```text
OK  转场有因果词      False
OK  呼应后半有回收    0/0
OK  结尾有状态动作    False
REVIEW: PASS
```

- **边界**：这是 review 单阶段的缺陷，不是说这五行稿也能通过完整 design/draft。事实检查还有独立步骤，不能说所有事实闸一起失效。
- **建议及验收**：改为明确的关键字参数和布尔类型契约；对因果、结尾、反转及事实锁分别加入正反例；对“不适用/缺失”明确区分，不能用 0/0 自动证明回收充分。

### E02 · P0 · Node 检查器报错，runner 仍然绿灯

- **位置**：`scripts/fuben_run.py:35–44`。
- AI 步骤只查输出有没有字面量 `[blocking]`，不正确区分命中规则与工具故障。
- **独立复现**：其余七步用真实 78；只把 AI checker 路径替换成不存在的临时路径。Node 真实返回 `MODULE_NOT_FOUND`、退出码 1，runner 却打印 `[AI-patterns] PASS` 并退出 0。
- 自动补一句 **“advisory only: 已通读”**，还把机器状态写成不存在的人工行动。
- **建议及验收**：调用 `--fail-on=blocking`；按结构化结果、退出码和工具异常分别处理。工具丢失、语法错误、输入不可读、超时、输出不可解析都要停止，不能伪装为 advisory。真正“已通读”必须来自有版本的人工/模型复核回执。

### E03 · P0 · 数据写入与读取契约已断裂

- **位置**：`作品/_数据_v2.csv`；`scripts/fuben_loop.py:367–428`。
- v2 表头 36 列、24 条记录，**13 条列数不等于 36**；其余还存在等宽错位，详见数据章节。
- 当前 `record/report` 指向旧 `_数据.csv`，没有接通 v2。旧表头 15 列，当前 `features()` 少一列且特征定义已改。
- **独立复现**：只对临时复制的 v1 调 `record(['78','10','100'])`，追加 **14 列**；再 `report()` 抛 `TypeError: unsupported format string passed to NoneType.__format__`。
- **建议及验收**：单一 schema/version；按字段名写入；类型、范围、列数校验失败就拒收；显式迁移旧表，不靠补逗号。作品 ID 与版本精确指定，不能 `glob('72_*')` 后取第一个目录。读写 round-trip、含英文逗号备注、缺值和多版本必须有测试。

### E04 · P1 · 机械 PASS 与发布准入之间缺少聚合验收

- **证据**：`AGENTS.md:54–66`、`skills/fuben-review/SKILL.md` 和 `scripts/fuben_run.py:46`。
- runner 自己已明确“机械通过后仍需人工审核”。因此**它不查审核报告本身，不是违反自身职责**。问题是整套系统没有一个可执行的发布入口，汇总人工审核、TTS、精读、新旧稿豁免、批准和版本。
- **边界探针**：临时复制 78，删除场面表，写 `VERDICT: BLOCK`，机械 runner 仍 PASS。场面检查器也把没有场面表一概视为旧稿而 SKIP。这里证明的是集成缺口，不是要求把文学判断塞进全部正则。
- **建议及验收**：保留机械 runner 的窄职责，另设 release verifier。它检查“必需证据是否存在且绑定当前 hash”，而不是猜“好不好看”；人审可给例外，但需 reviewer、理由、适用版本与失效条件。

`_数据_v2.csv`：36 列，24 条数据，13 条变长。普通 `csv.DictReader` 不会自动修复，而会默默把值放进错列。

- **72 行**（文件第 14 行）：目录中的英文逗号未正确转义，解析后 `likes='published'`、`play_pv='28'`、`like_rate_permille='1033'`。
- **62 等早期行**：列数恰好 36 仍然错，备注文字落到 `字数`，`2365` 落到 `呼应对`，`legacy_unverified` 落到 `快照时间`。
- **78 行**：39 列，备注中逗号继续拆列；当前 v2 稿与旧 1,907 字/298 秒/13.1 的记录未同步。

因此本报告的后台数值复算取自 D0 的可读表格，**没有拿错列 CSV 直接算分析结论**。

### 6.3 “完播 proxy”不是完播率

`平均播放时长 ÷ 成片时长` 得到的是平均观看比例，无法推算“看完的人数占比”。它可以保留为描述指标，建议字段名 `mean_watch_fraction_pct`；真正 `complete_rate_pct` 应来自后台定义，缺失则留空。

最直观的反例：平均观看都为 18 秒，长片 446 秒时比例是 **4.0%**，改成 60 秒时就是 **30%**。观众多看一秒都不需要，该指标便大涨。于是“切条达到 ≥10% 就证明载体论”的判据无法排除分母效应。

点赞/播放也只是该口径的互动比率，不等于每个独立观众的认可比例，更不能证明已划走的大部分人也认可。

### 6.4 不成立的归因

D0 `:18–23,42,60` 与后续签署中，下列结论需要撤回或降为假设：

| 仓库说法 | 为什么证据不够 | 目前可以说什么 |
|---|---|---|
| 三条都超过 500，正式否决账号问题 | 某个诊断阈值未触发，不等于所有账号问题被排除 | 这三条收到一定播放，未触发原先的低播放报警条件 |
| 2,094 播放＝进过二级池 | 未见官方规则/来源分布/完整时间序列 | 播放量为报告值 2,094，推荐层级未知 |
| 72 点赞率较高，所以剧本不是主因 | 样本小、受众不同、幸存互动不能解释跳出者 | 保留下来的部分播放产生了互动，值得定位哪些段落/观众 |
| 每条长片都会压制下一条；下降 46.4% 就是证据 | 无对照，混有题材、时段、受众、发布历史等变量 | 长度及首屏是值得实验的因素，不是已证唯一因果 |
| 长版与切条是第一次干净 A/B | 时长、首屏、删减情节、CTA、发布时间同时变化 | 是探索性版本比较，不是隔离单变量的随机实验 |
| 原文在库就等于“已被结果验证”，所以能证明签名句/合集有效 | 未绑定来源视频、观察窗口和数据 | 可证明这种写法在语料中出现，不能证明由它带来流量 |
| 无签名句的片都稀释定位 | 是把一个尚未验证的强因果替换成另一个 | 签名句可作品牌策略和可测假设，不能充当算法定律 |

**我同意尝试更短、更早给冲突的版本；不同意把试验方向包装成已经完成的归因。**看到这些数字，首要动作应是修表、拿真实留存、对齐快照，而不是再写一套“算法只认”的教义。

### 6.5 应当建立的数据最小集

把“一条大宽表同时存作品、版本、媒体、快照、评论”拆成最少三个概念：

1. **作品/版本**：`work_id, variant_id, script_sha256, approval_id, genre, target_audience`。
2. **成片/发布**：`media_sha256, duration_measured_sec, title, cover_variant, platform_video_id, published_at_with_timezone, organic_or_paid`。
3. **指标快照**：`snapshot_at, age_minutes, source_evidence_ref, data_quality, play_pv, viewer_uv_if_available, retention_t3/t5/t15, avg_watch_sec, actual_completion_rate, comments/shares/saves/follows, traffic_sources`。

- 不可得指标留空，不能用 0 或代理量冒名替代。
- 同一作品多个快照追加记录，不能覆盖历史。
- 评论分桶保留原始样本/抽样窗口，区分“不懂规则、嫌长、人物不可信、被打动、事实纠错、对号入座”等；小样本只作线索。
- 可先用严格 schema 的 CSV/JSONL 或 SQLite，没必要先上复杂平台。
- T+24h、T+72h 等固定窗口用于比较；早期值可做运营监控，不仓促做创作因果结论。

## 七、如果由我负责 Agent 落地，会怎么改

### 7.1 先做一个可靠的小闭环，不先追求更多 agents

```text
topic_selected
 → outline_approved（批准的文件 hash）
 → draft_ready（具体变体 hash）
 → mechanical_pass（检查器版本 + 完整结果）
 → editorial_pass（独立审查或明确 self-review）
 → media_qa_pass（实际音频/视频 hash、实测时长、时间码 findings）
 → release_approved（账号主授权）
 → published（平台回执和 video_id）
 → measured（同窗口指标与来源证据）
```

稿件改动后，旧的机械/编辑/媒体验收按依赖失效；批准大纲不等于批准当前成片。`PASS / FAIL / ERROR / NEEDS_REVIEW / NOT_APPLICABLE` 应分开，不能凡不是 blocking 就 PASS。

### 7.2 工具、提示与状态各管一件事

- **Skill** 管目的、写法、需要的证据和人工 rubric。
- **程序** 管类型、算术、文件/引用/版本、退出码、明确可判的规则。
- **模型 reviewer** 管因果、角色知情、观众理解成本、场面功能；每条 finding 引用当前正文 span，不准只写好坏分数。
- **媒体工具与人审** 管读音、停顿、字幕、画面、音乐遮盖、实际前 3/15 秒。对文字估时保持不确定性。
- **发布器** 独立权限，先生成待发布草稿/预览；没有账号主授权不能发布。浏览器会话和平台凭据不进入正文、报告或通用模型上下文。
- **状态存储** 记录 `run_id, work_id, variant_id, input_hash, output_hash, tool_version, reviewer_mode, fallback_reason, evidence_refs, duration/cost, retry_count`。结构化输出的 schema 验证失败要重试或停下，不靠文本找 PASS。

若使用支持工具调用与结构化输出的模型，应让工具返回机器可校验的结果，不把一长串角色扮演文字当调度器。外部网页/原文按不可信资料处理，不能执行其夹带的指令。

### 7.3 独立审查怎么做才有效

先让作者产出定稿和可引用事实；reviewer 读题目、事实证据、正文，不先读作者“已过闸、9/10”的自评。必要时事实审、观众理解审分别运行；无多 agent 能力就诚实标注 self-review，不伪造独立性。

同一模型能做不同维度，但“换三个角色名”不保证独立。比模型数量更重要的是输入隔离、证据引用、分歧处理、修后复核和盲评。返修应有轮次/成本预算；反复无新增改善时提交人决策，不无限写入新教义。

### 7.4 适合保留与退出硬门的东西

- **继续硬门**：输入缺失、程序故障、金额/日期/身份硬矛盾、未经批准的版本、必须的授权/成片 QA 缺失、显式账号禁令。
- **改为可解释 advisory**：单字感官计数、固定情绪峰值百分位、统一数字密度/行数、所有题材同一种结尾。
- **不从脚本输出**：“已通读”“保证爆款”“算法一定给二级池”“账号没有病”。这些要么是人的行动，要么是目前没有证据的推断。

## 八、实施次序与验收条件

### 第一阶段：1–2 天，先修可信性

1. 修 E01/E02，补正常/异常/缺输入/超时/不可解析测试。
2. 停止对当前 v2 做自动归因；按来源逐行重建 schema，未确认数据隔离。
3. writer/reader 统一版本和命名；拒绝静默错位；补 CSV round-trip 与迁移测试。
4. 将“固定十篇回归”改名并补当前候选稿集，不要求所有遗留作品马上迎合新契约。

**验收**：任何 checker 崩溃都不 PASS；已知 False 条件不打印 OK；所有已接收数据类型/列数/单位有效；生产指标能回到具体文本和来源快照。

### 第二阶段：一周内，做一篇完整、可证明的交付

1. 定义副本 profile 和发布 manifest，消除通用短篇契约冲突。
2. 修 75/76/77/78 的确定性文本问题及 78 来源范围/切条承诺，不为过闸改掉作品个性。
3. 优先选择一个受众明确的版本走完整制作，不同时新增十篇来掩盖流程欠账。
4. 真实 TTS、实测秒表、手机预览、逐镜 QA；最后才让账号主批准发布。

**验收**：输入、审稿、声音、视频、批准、平台回执全部能通过同一 variant/hash 链定位；缺任何必需项则状态停在 PROVISIONAL，而非“发布可带”。

### 第三阶段：随后 2–4 周，验证内容假设而非宣布定律

- 小批量、同账号、尽量配平题材/时段/发布条件；一轮优先测试一个主要改变，例如首屏版本，而不是同时更换故事、封面、语速、片长。
- 若测时长，明确这是“删减后整体版本”的效果，不假装只改了一个数字。
- 预先确定主要指标和护栏：真实 3/5/15 秒留存、平均观看秒数、真实完播、分享/收藏/关注，以及负面误解/事实纠错；不用一个比例决定全部成败。
- 初期多篇只能筛选方向；是否足够统计判断取决于曝光、基础率、目标效果与方差，不承诺“发三条就证明”。
- 对好/坏案例做盲评，先归到特定题型，再考虑修改 skill；保留变更原因、反例与回滚条件。

**验收**：每条结论明确写“观察/假设/较强证据”，能展示对照和不确定性；没有真实证据便不升级为硬规则。

## 九、面试结论与我会追问的问题

### 分维度结论

| 维度 | 面试评价 |
|---|---|
| 内容研发与素材组织 | **有实作价值**。不是空模板，若干新稿已有明显叙事能力 |
| Skill 设计与拆文复用 | **方向正确、整合未完成**。需要 profile、引用证据与规则优先级 |
| Agent 工程可靠性 | **原型阶段**。不能仅凭现有 PASS 承诺无人值守交付 |
| 抖音数据分析 | **先补基础契约**。当前表和归因不能支持强运营决策 |
| 最后一公里交付 | **文稿准备不等于成片准备**。需要真实媒体、QA 和发布回执 |

这不是“仓库没有用”，也不是“已经接近稳定爆款机器”。更准确的判断是：**编辑经验跑得比验证工程快，规则数量跑得比证据积累快。**下一轮价值最大的是收敛、修复和验证，不是继续加一层更长的提示词。

作为面试交付，我会要求负责人当场回答并演示：

1. 如果 Node 检查器损坏，为什么你的系统绝不会给 PASS？展示失败路径。
2. 给一份没有因果、没有结尾状态动作的稿，review 哪一步会失败？用反例说明，不念 rubric。
3. 同一稿改成 40 秒后，平均观看比例上升，你如何排除只是分母变化？
4. 78 的哪一条公开来源能支撑哪一句事实？哪些只是虚构合成？
5. 当前发布稿是哪一个 hash？谁批准、谁听过、哪个 video_id、哪个 T+ 快照？
6. 拆文库里的疑似 ASR 截断，凭什么是可复用写法而不是数据错误？
7. 当一篇好稿与“峰值必须在某百分比”的规则冲突，你用什么证据决定改稿还是改规则？

**最终建议：保留内容资产和证据导向的方法；先修假通过、数据 schema 和发布状态链，再用实际成片与同窗口平台数据决定哪些文风规则值得留下。不能对爆款作保证。**
