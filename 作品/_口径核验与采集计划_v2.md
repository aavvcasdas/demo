# 10–20 赞 vs 30–90 赞 vs 过百：口径核验、v2 数据表与 7 天采集计划

> 接手人交付物（任务一）。作者：2026-09-18。
> 红线自查：本文所有"仓库内数字"均为亲自读文件/跑脚本所得；**未编造任何后台数据**；后台未拿到的字段一律标 `待取证`。

## 一、口径核验清单：三个来源逐条对账

### 1.1 三源现状（仓库内可验证的部分）

| 源 | 原话/数据 | 记录时间 | 记录工具 | 可验证性 |
|---|---|---|---|---|
| A 账号主口述 | 「所有视频现在只有 10–20 赞」 | 2026-09-18 早 | 无（微信口述） | 不可验证——「所有」是未证全称；「现在」无快照定义 |
| B `作品/_数据.csv` | 57=60、62=90、58/59/60/61=30；播放列**全 0（从未采集）**；57 备注「疑似推流」、62 备注「六篇中最好 均未过百」 | 无时间列。备注文风与 `_复盘_57-65` 同期 → 推定 2026-09-13 | `fuben_loop.py record NN 点赞`（无时间戳参数，`record()` 源码 L359–377 可查） | 部分可验证（数值+备注自洽：60/90<100 且备注称"均未过百"） |
| C `作品/_复盘_57-65_数据归因.md` | 标题「为什么只有 57/62 **过百**赞」；表：57 ">100（推流叠加）"、62 ">100" | 文内标 2026-09-13 | 人写 | 与 B 直接冲突（同为 09-13，数值一个 60/90、一个 >100） |

### 1.2 矛盾点逐条

1. **A vs B（题面矛盾）**：10–20 赞 vs 30–90 赞。**点赞不可逆**（视频不删不锁就不掉赞）→ 两批数字**必然不是同一批视频**：B 只记了 57–62（六行）；63–72 时代 CSV 无行。A 的「所有」最合理解释 = 「最近这批（66–72+，未入表）」。→ 这不是数据错，是**覆盖面缺口**：数据回流在 09-13 后停转，账号主看到的是最新实况，表是三个月前（对 66–72 而言）的化石。
2. **B vs C（同日矛盾）**：复盘称 57/62 过百，CSV 记 60/90。两种仲裁可能：(a) 复盘写作时看到的是 T+N 更新值而 CSV 记的是发布当日、且 CSV 后来没回填；(b) 复盘把"评论区/口头说的破百"当数据写进了报告。仓库内无法裁决 → 后台证据（下节）。
3. **B vs 播放列**：schema 里本来就有「播放」列（record 的第三个位置参数），六行全 0——**唯一能算 like_rate 的列从未被采集**。"找不到原因"的技术性根源：全库只有点赞绝对值、没有分母。
4. **A vs C 隐藏推论**：若 C 的"过百"为真、且 A 的"10–20"只指新稿，则账号曲线为 60–90 →（可能 >100）→ 10–20，**账号在衰减**；若 C 为假（以 B 为准），曲线为 30–90 → 10–20，同样衰减但幅度小。两种世界线对"该修稿还是该修号"的处方完全不同 → 必须仲裁。

### 1.4 拿到证据前，三份数据按什么折扣用

- **A 账号主口述**：按「最新批次（66–72 时代）的当前读数」用，**不接受"所有"**。用途：定优先级（先修观测再修稿）；不得用于任何"内容质量"结论。
- **B CSV**：按「record 当日的一次性快照」用（无时间列 → 只能证明**同批相对排序** 62>57>其余四，不能证明绝对水位）。播放列与 10 个特征列保留；点赞绝对值全部标 `legacy_snapshot_unverified`。
- **C 复盘"过百"**：数字降级为**待证假设**；但其剧本层定性（59/60 撞正主、58 无代价、61 流水账、收束加温）不依赖点赞量级，**继续按有效假设使用**。
- 总折扣原则：**当前仓库 = 零条可用于定量归因的后台数据。所有归因先降级为假设，新数据进表前禁止任何"因为 X 所以扑"的句式。**

### 1.5 加分项：仓库里第 4、5 处隐藏自相矛盾（均为实测复现）

- **#4（备注列 vs 复盘，题眼）**：CSV 62 行备注「六篇中最好 **均未过百**」是 record 当天写下的自我证词，而**同一天的复盘**通篇以「57/62 过百」为数据底座、并把 §14.1「痛要是结构的不是人际的」等 skill 升级**归因到这个"过百"上**（复盘 L27：「62 … §14.1 第 2 条在 62 得到验证」）。→ **现行 skill 至少两条升级规则的"数据验证"建立在同库另一文件明确否认的数字上。** 即使不仲裁谁真谁假，"验证"的措辞本身应降级为"与排序一致"。
- **#5（复盘引用口径 vs 工具复跑）**：复盘 L4 称「57–60 全 FAIL **6 项**」；复跑 `check_fuben_texture.py` 实测 57=FAIL 6、**58=FAIL 7**、59=FAIL 6、60=FAIL 6（61 确为 PASS，此条复验成立）。→ 复盘里的数字有一个复现不出；同文件「61 唯一 PASS 却**最差**」在 CSV 里是 30 赞与 58/59/60 **并列**，「最差」无数据依据（并列垫底）。
- **#6（顺带）**：README 合规段"45/45 通过"在旧命令下输出 5/54（长篇条目混入）——已由任务三 A 的 `--scope` 修复对齐。

## 二、`_数据.csv` v2 schema

**设计目标只有一条**：让"死法"三分。列 = 24（迁移不丢 v1 信息；`record` 现有列保留原名以兼容 `report()`）。

| 列 | 采集来源 | 回答什么问题 |
|---|---|---|
| `id`,`目录`,`字数`,`呼应对`…`人际词`（v1 原列，14 个） | `fuben_loop.py record`（自动算特征） | 剧本特征侧（v1 的全部遗产） |
| **`published_at`** | 后台·作品管理页每条视频的发布时间 | 对齐三源时间轴（本次矛盾的直接病灶） |
| **`snapshot_at`** | 手填，`2026-09-25T09+T7d` 格式 | 每个数字是第几天的读数——**没有这列，任何点赞数字都无法比较** |
| **`play_pv`** | 后台·内容数据·作品数据导出「播放量」 | 冷启动判据：<500=没给量（死法①）；≥1000=给了量 |
| **`source_rec_pct`** | 后台·观众分析·流量来源「推荐页」占比 | 给了量但来源异常（关注页>50%=私域消化，破圈失败） |
| **`retention_t5s_pct`** | 后台·单视频·留存曲线，读 t=5s | 首帧判据：<45%（暂定，7 天后用实测分布重定）= 死在首帧（死法②） |
| **`first_cliff_sec`** | 同上，曲线第一次可见跳水的秒数 | 中段判据+对账：跳水位≈剧本无爽点区=死在剧本；跳水<15s=死在制作（配音/画面/封面首帧） |
| **`complete_rate_pct`** | 后台导出「完播率」 | 死法③主体：留存 OK 但完播 <12%（暂定）= 留了没看完 |
| **`avg_watch_sec`** | 后台导出「平均观看时长」 | 与成片时长之比 = 有效完播的稳健替代 |
| `likes`,`comments`,`shares`,`saves`,`follow_gain` | 后台导出 | 互动漏斗：转/赞>1.5 说明内容有传播位；评论关键词另表 |
| **`like_rate`** | 公式列 = likes/play_pv×1000（‰） | **跨量级可比的质量指标**——v1 点赞列的唯一救法（见下） |
| **`comment_rate`** `share_rate` | 公式列 | 同上；share_rate 对"转发=清算类爆款引擎"直接验证 57 复盘假设 |
| `gate_hype_density`,`gate_first_big_pct`,`gate_fail_count` | `fuben_hype.py`/`fuben_run.py` 输出解析 | 发布前设计值 → 与 `first_cliff_sec` 对账（**本仓库独有优势：把预测位置和实际跳水点接起来**） |
| `duration_sec` | 成片实际时长（剪映导出信息） | 字数≠时长；3 分钟线由它裁决 |
| `data_quality` | 手填枚举 | `backend_export` / `manual` / `legacy_unverified`——三源矛盾的制度化免疫 |
| `video_product_version` | 手填 | 同稿不同制作版本（配音/封面）各占一行 → 任务四实验 C 的载体 |

**点赞列还能不能救？** 绝对值救不回（旧行无播放分母，永远无法算 like_rate）；能救的是它的**用途降级**：① 旧 6 行只进「排序+定性」层（`data_quality=legacy_unverified`，v2 表照录并在 `备注` 保留原话）；② 新行一律以 `like_rate`（‰）替代绝对点赞做跨稿比较，绝对值仅作传播规模参考；③ v1 里「62 比 57 好」这类排序判断保留有效——排序对口径不敏感，量级对口径敏感。

v2 表已建：`作品/_数据_v2.csv`（6 行 legacy 迁移 + 58b/64v8/65v7/72 紧凑版/66v6 五条 planned 空行）。`fuben_loop.py record` 暂不改写（红线：不顺手重构），7 天窗口内 v2 手填+公式列用表内计算；实验跑通后再一次性把 `record` 升级为写 v2 列。

**每天记录什么**：每条 T+2h、T+24h、T+7d 三个快照进 `_数据_v2.csv`（10 分钟/条·天；账号主手机截图即可，我代填表）。D0 先做：把 **66–72 已发存量**的后台数（若已发）补进表——这可能直接替代一半实验。

**第 7 天能得出**：
- 这批改稿是不是还在拿冷启动量（play_pv 分布）→ 账号侧/内容侧的**第一刀裁决**；
- 每条的死法三分（play/首帧/中段），以及 `first_cliff_sec` 与 `gate_first_big_pct` 的相关方向——v10 规则第一次被真实数据检验；
- like_rate 在 5 条内的相对排序（不再问"过没过百"，问"‰ 水位和漏斗形状"）。

**第 7 天得不出**：任何"能过百/能爆"的绝对结论（n=5 只够方向）；账号权重结论（需 30 天序列 + 违规史核查）；"57/62 到底过没过百"（只能等 E1 后台历史导出）；制作层与剧本层的完全分离（要等任务四实验 C 的第二条腿：同稿不同配音版）。

**预注册判定式**（防事后解释，写进假设卡同级别）：若 5 条中 ≥3 条 play_pv<500 → 主因判账号/权重侧，剧本迭代暂停两周；若 ≥3 条 play_pv>1500 且 retention_t5s<45% → 主因判产品首帧层；若 ≥3 条 t5s>55% 且 complete<12% → 主因判剧本中段，回 fuben_hype 收紧位置闸。三分之一的数据就能转舵——**这就是"能找到原因"的意思。**
