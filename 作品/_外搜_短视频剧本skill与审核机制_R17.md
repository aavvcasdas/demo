## 二、剧本审核机制六家（本轮核心问题：他们怎么审）

### 1. eternityspring/shuohao-skills（3566★，push 2026-09-14，Apache-2.0）——确定性质量门

**哲学（原话）：「模型自评容易自圆其说，脚本检查不会。」** 52 道质量门全由零依赖 Node 脚本检查，不花模型额度：大纲 14、美术 11、**剧本 10**、分镜 17。剧本 10 门：每集时长 ±15%（按语速确定性折算）、单句 ≤35 字、说话人合法、钩子悬念落纸、hookBeat 认领冷开场（前 3 拍内兑现）、每场至少一个动作节拍、爽点认领（防改稿改丢爆点）、角色/场景/光照/道具对账上游 JSON。地基设计：**台词必须是结构化数据（说话人+台词+语气逐条），不能散文**——这是全部确定性检查的前提。另有**体检模式**：对已有大纲跑 14 道门找问题（存量诊断，不是只管新稿）。每 skill 带 selftest.mjs，1 秒跑完不调模型。

### 2. zenstory-ai/drama-skills（2059★，push 2026-09-18，MIT）——独立审查技能

11 个 skill 里**审查是独立技能**（short-drama-review），规矩三条：
- **审查与修改分离**：「只定位问题、影响和必须达到的修订结果，不在同一轮替 owner 修改来源」；
- **独立 reviewer 优先**：「优先由未参与当前版本创作的 reviewer 执行；条件不允许时可以自检并如实说明」；
- **无证据不打分**：「不能只说『AI味』『不够电影感』或给无证据分数」——每个 finding 必含：位置/短引文/观众影响/必须达到的修订结果/owner/严重程度。
- 结论四档枚举：`APPROVE / APPROVE_WITH_NOTES / REVISE / PROVISIONAL`（关键输入不足时明说，不硬判）。先查可证明事实（五文档 ID/引用/时长一致、对白有画面承载、道具状态连续、私有信息泄漏），再跨文档综合。
- **有实跑**：PR #126 拿 20 章原著真跑出 EP001 五份文档+8 镜实产+24 秒成片，RUN-LOG 逐条记撞坑（含驳回与作者自错）。

### 3. YingaoZhang/short_drama_agent（6★，push 2026-07-06）——审改分级路由

LangGraph 六 Agent 链（统筹→世界观→主笔→**综合质检**→改写→分镜），质检结果分级路由：`FATAL` 打回世界观层 / `SEVERE` 打回单集剧本 / `MINOR` 改写后复审 / `PASS` 进分镜；另有大纲/初稿后的人工断点。

### 4. chaosinu7-svg/life-sim-video-pipeline（push 2026-08-12）——内容错误与自动质检的绝缘铁律

作者自用日更系统，从两集真实交付反推固化。**铁律原文：「渲染成功、脚本零报错、自动质检全绿，但成片是坏的。」** 其自动质检只管黑帧/静音/响度/分辨率/True Peak，全绿的同时成片里有七个内容错误：标题卡整段丢失、出现剧本里不存在的人名、屏幕数字与旁白对不上、合同日期矛盾、手机屏幕朝镜头而人物视线也朝手机（等于看背面）、结尾记账本换了一本、人物该失眠却在笑。**结论：「交片前必须逐镜看。」** 16 条事故每条含复现方法与规避写法。另有硬数据：手册语速 3.4-4.2 字/秒，实测 4.68——排分镜前先跑一次 TTS 量真值，否则片长估错三到六成（与我们 6.4 实测 vs jiaoben 3-4 同款教训）。选题规律：同账号同制作播放差 **1500 倍**（184万 vs 1167），「惨不产流量」。

### 5. luckyxpw/life-script（push 2026-08-12）——人工门 + 完整性绑定

`source story → 完整终稿展示 → 明确批准 → 角色锚批准 → 开场预览批准 → Studio 预览批准 → 渲染 QA`。`SCRIPT_APPROVAL.json` 用 **SHA-256 绑定 SCRIPT.md 的精确字节**，批准后任何改动即失效断点。

### 6. sergebulaev/tiktok-skills（41★，push 2026-09-17，MIT）——预拍审计（TikTok 侧）

tt-humanizer 带 `--mode audit` 预拍检查，**阈值显式可复现**，blocker/warning 分级：B2 payoff 前不许问候/logo、B4 hook 与屏字不许同词、B5 hook 承诺必须兑现、B7 AI 词汇簇按节拍密度计分（3+ 才 fail，一个算 slip）、W1 hook 里没有带指代对象的数字=警告。明确声明「不承诺骗过检测器」。

## 四、对照我方：验证了什么、能偷什么、不偷什么

**验证（3566★ 与 2059★ 两仓替我们背书）**：shuohao「脚本检查不模型自评」=我们七闸+test_gates 红样同款路线；chaosinu7 实测语速戳穿手册值=我们 6.4 实测的坚持；zenstory「审查不代改+独立 reviewer+无证据不打分」=我们 diff-or-撤回+R15 双方互审；「体检模式」=我们全库 `--all` 跑法。**我们独有（六家+五仓全查过，均无）**：事实锁 L0 对真实世界信源对账（他们最多对账上游 JSON）、45 篇一手语料密度带、§3.9 状态三问刻画层（内容层审核只有 chaosinu7 的「逐镜看」沾边）、发布数据 D 批回流复检规则。

**可偷清单（全部 advisory/工具层，0.6 条款内，待账号主点头再动手）**：
1. **体检模式**→ 写 `scripts/fuben_health.py`：对已发布/在库全部作品跑一遍七闸+密度+场面表，出单页体检报告（工具层，不新增阈值）；
2. **结构化 finding 模板**（zenstory）→ 审核报告统一 schema：位置/证据/影响/修订结果/owner/严重度 + 四档结论枚举（含 PROVISIONAL「关键输入不足」——我们现在缺这个档，容易硬判）；
3. **逐镜人审清单**（chaosinu7 十六条）→ 等进入 TTS/成片环节时，发布前人工项按它建「成片逐镜清单」；
4. **审改分级语义**（FATAL/SEVERE/MINOR）→ 我们 BAD 停点已有事实分级，借它的命名让审核报告好读；
5. **战略呈报**：真实人生故事线开不开（核实成本高，但恰是事实锁强项；「剧本人生」已验证百万粉天花板与商单模式）。

**不偷**：Tinxyoo 术语密度原则（与我们语料实证和 R2 去模板相反）；「惨不产流量」当铁律（单账号样本，我们 D 批数据自己会说话）；任何「一键成片」全自动（chaosinu7 铁律+我们 N=6 的账号权重都反对）。
